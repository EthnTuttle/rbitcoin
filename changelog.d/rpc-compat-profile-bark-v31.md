- **`--rpc-compat-profile bark-v31`: opt-in named RPC compat claim (regtest only).** `--rpc-compat-profile bark-v31` (conf `rpc_compat_profile=`, the only accepted value; there is deliberately no env form and no free-form version integer) makes `getnetworkinfo.version` report **310000** — the floor the ark/bark server at `c419159` gates on — while `subversion` keeps the real `/rbitcoin:<semver>/` identity, `protocolversion` stays 70016, and every other `getnetworkinfo` field is unchanged. The response appends a structured `rbitcoin_compat` object (`profile`, `claimed_version`, `package_dialect: "core-is-child-with-parents"`) and startup logs `rpc_compat_profile=bark-v31 claimed_version=310000 software=rbitcoin software_version=<real>`, so the claim is explicit and auditable, never a disguise. The profile selects the existing Core `IsChildWithParents` `submitpackage` dialect (the `RBITCOIN_RPC_PACKAGE_DIALECT=1` behavior); an explicitly-off `RBITCOIN_RPC_PACKAGE_DIALECT=0` together with the profile is a startup config error, and any network other than regtest fails config validation before the datadir or store opens. Default is off: `version` stays 190000 and no `rbitcoin_compat` key appears. The claim is deliberately narrow — read-only RPC surface shape for probed lab clients, not Core v31 parity: funded broadcast/mempool behavior stays unproven by read-only probes, and known surface mismatches stay mismatched (`getmempoolinfo.maxdatacarriersize` is null where the selected modelling consumer expects an integer). `docs/rpc.md` owns the surface contract (see "Opt-in named compat profile"); `COMPAT.md` owns the intentional-difference statement.
